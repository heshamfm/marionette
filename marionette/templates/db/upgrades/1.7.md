# Marionette 1.7: rules to add to the owner's manual

The upgrade program changes the programs and the data. It never writes the owner's manual: the manual is the owner's.
The session that applies the upgrade shows the owner these rules, in the owner's language, and adds each one the owner
approves to MANUAL.md (the section named), raising its version and logging the decision. Scheduled runs name them in
their message until the owner decides.

## Section 3, item rules (after "Next step with the owner")
Who holds the next step decides what is the owner's: a message lists as waiting for the owner only the items in the
brief section ON THE USER, never an item held by anyone else, whatever its type or date. Handing an item over to
another party rewrites, in the same change, its title for the new holder (what they do next) and its deadline and
next check; the program refuses it otherwise. A title is changed with act --action rename, quoting the source.

Checks due: when an item's next check comes, the run that meets it looks for news in the live channel that same day,
then records what it found, or moves the next check forward saying what it checked. An open item always keeps a
deadline or a next check. The end-of-run check names every check left unhandled and every open item with no date.

## Section 4, the periodic run (a new step before the reminders)
Checks due: every item in the brief section CHECKS DUE, oldest first: look it up live, then record what was found,
or move the next check forward quoting what was checked.
In the message, the list of what waits for the owner is the brief section ON THE USER and nothing else.

## Section 5, interactive sessions
Shown as saved means printed from where it is saved: whatever the owner is told was recorded (an issue, a question, a
reminder, a draft, a decision) is shown as the program prints it back (mrun.py issue, item), never as a text written
beside it. When the text changes, the record changes first (issue-append, act edit, act rename).

Problems in how Marionette itself works are recorded at once in the issues register, in its fixed template
(tools/db_usage.md, Issues register), never handed over as a prompt to copy; more to say on one is added with
issue-append, never a second issue.

Carrying out a rule the owner decided: write it in the owner's words. A condition the owner did not state is never
added on the way; if the rule cannot be carried out without one, ask first.

## Section 6, the auditor
It also works every open issue (mrun.py issues): finds the cause, fixes what it is sure of and resolves the issue
saying how, asks the owner about the rest, and looks for the similar cases each time.
